# Локальная оценка pipeline (доработка после хакатона)

## Зачем это здесь

Во время хакатона `search`-сервис обращался к двум внешним HTTP API,
которые предоставляли организаторы: dense-эмбеддинги (`Qwen/Qwen3-Embedding-0.6B`)
и rerank (`nvidia/llama-nemotron-rerank-1b-v2`) по адресу `83.166.249.64:18001`.
После окончания хакатона этот адрес недоступен, а закрытого тестового
набора вопросов (по которому реально считались `Recall@50`/`nDCG@50` на
конкурсе) в публичном шаблоне никогда не было — в `data/` лежит только
сам чат.

Эта директория поднимает **локальные замены** обеих моделей и весь
недостающий "оркестратор" (то, что раньше делала закрытая система
проверки), чтобы можно было прогнать полный pipeline офлайн и получить
честные, воспроизводимые числа по формуле конкурса.

Код `index/main.py` и `search/main.py` — то, что реально было отправлено
на хакатон — не менялся ни на строчку.

## Чем заменили

| Было (хакатон) | Стало (локально) |
|---|---|
| Qwen3-Embedding-0.6B (1024-мерный) через внешний API | `fastembed.TextEmbedding("sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2")` — мультиязычная (включая русский), 384-мерная, всего 0.22GB |
| nvidia/llama-nemotron-rerank-1b-v2 через внешний API | `fastembed.TextCrossEncoder("jinaai/jina-reranker-v2-base-multilingual")` — единственный мультиязычный reranker в fastembed; берём квантованный вес (`onnx/model_quantized.onnx`, 0.27GB против 1.1GB) через `add_custom_model` |

Оба варианта работают через ONNX Runtime (уже используется в проекте для
BM25-модели) — новых тяжёлых зависимостей вроде `torch` не потребовалось.
Реализация — `ml_service/main.py`, поднимается как ещё один сервис
в `docker-compose.yml` (`ml-service`), на него же теперь указывают
`EMBEDDINGS_DENSE_URL`/`RERANKER_URL` по умолчанию.

Из-за другой размерности dense-модели (384 против 1024 у Qwen)
`eval/index_corpus.py` перед индексацией пересоздаёт Qdrant-коллекцию
под фактическую размерность — код `index/` и `search/` это никак
не затрагивает (он с размерностью не работает).

## Как запустить

Нужны только **Docker** и **Python 3** — никаких pip-пакетов, всё на
стандартной библиотеке.

### macOS / Linux

```bash
export OPEN_API_LOGIN=dummy
export OPEN_API_PASSWORD=dummy    # ml-service не проверяет авторизацию, но search этого требует
docker compose up --build -d      # поднимет qdrant, index, search, ml-service, web-ui
                                  # первая сборка качает ~0.5GB моделей

python3 eval/index_corpus.py      # проиндексирует data/Go Nova.json в Qdrant
                                  # (тонкий клиент к API web-сервиса)
python3 eval/run_eval.py          # прогонит eval/questions.json и посчитает метрики
```

Интерфейс проверки поднимается вместе с остальными сервисами:
http://localhost:8090 (документация API — `/docs`).

### Windows (PowerShell)

Те же шаги, отличается только синтаксис переменных окружения:

```powershell
$env:OPEN_API_LOGIN="dummy"
$env:OPEN_API_PASSWORD="dummy"
docker compose up --build -d

python eval\index_corpus.py
python eval\run_eval.py
```

Bash для запуска не нужен: все скрипты явно работают в UTF-8 и не
используют платформозависимых вызовов. Единственный bash-скрипт —
`eval/ablation.sh` (сравнение конфигураций); он не нужен для запуска
системы, а на Windows выполняется через Git Bash или WSL.

### Веб-интерфейс

`web_service/` — отдельный FastAPI-сервис в docker-compose
(`web-ui`, порт 8090) для ручной проверки работоспособности.
Сам `/search` возвращает только `message_ids`, по которым глазами ничего
не оценишь; UI подставляет к ним реальные тексты сообщений, показывает
порядок выдачи и время ответа, а для вопросов из `questions.json`
подсвечивает ожидаемые ответы — сразу видно, на какие позиции их
поставил поиск. Сверху — статус всех сервисов и число чанков в Qdrant.

### Слой генерации ответа (опциональный)

`web_service/answer.py` замыкает RAG-контур: берёт верхние найденные сообщения
и просит локальную LLM собрать из них связный ответ со ссылками на
источники — вместо того чтобы заставлять человека читать выдачу целиком.

**На метрики это не влияет никак.** `Recall@50` и `nDCG@50` считаются по
`message_ids`, которые формирует `search/`; генерация происходит после и
в конкурсное решение не вмешивается. Это демонстрационная надстройка,
показывающая продукт целиком, а не улучшение поиска.

Работает через Ollama (по умолчанию `qwen2.5:3b-instruct`):

```bash
ollama pull qwen2.5:3b-instruct   # ~1.9GB, один раз
docker compose up -d web-ui
```

Ollama работает на хосте нативно (в контейнере нет доступа к GPU Apple
Silicon), сервис обращается к ней через `host.docker.internal`.

Слой **полностью опционален**: если Ollama не запущена или модель не
скачана, `is_available()` вернёт False, блок ответа просто не появится,
а поиск продолжит работать как обычно. Модель и адрес переопределяются
переменными `LLM_MODEL` и `OLLAMA_URL`.

Предохранители против выдумывания фактов: в контекст идут только реально
найденные сообщения (не более 8), системный промпт требует ссылаться на
источник у каждого утверждения и прямо разрешает ответить «в найденных
сообщениях ответа нет», температура снижена до 0.2, заданы стоп-строки
(без них модель дописывала к ответу следующую пару вопрос-ответ от себя).
Под ответом всегда печатается список источников — видно, из чего он собран.

Отдельно: в контекст модели цитаты **не попадают**
(`render_message(include_quotes=False)`). Процитированный текст писал не
автор сообщения, а собеседник, и он же лежит в исходном сообщении
отдельно — в контексте это выглядело как один и тот же текст от двух
разных людей, и модель путалась в авторстве.

### Демонстрационный чат

`data/demo_chat.json` — синтетический чат платформенной команды
(33 сообщения, 6 участников) для показа работы системы. Данные
вымышленные и к анонимизированному `Go Nova.json` отношения не имеют:
он нужен, чтобы демонстрировать поиск, не трогая корпус, на котором
посчитаны метрики.

Темы подобраны так, чтобы показать разные стороны поиска: инцидент с
номером `INC-2291` (точный термин), выбор брокера сообщений (ответ
размазан по обсуждению), хранение секретов (вопрос-ответ), откат
релиза (причинно-следственная цепочка).

```bash
python3 eval/index_corpus.py demo_chat.json
```

Переключить можно и селектором в интерфейсе — скрипт делает ровно тот
же вызов.

Коллекция в Qdrant одна, поэтому после демонстрации нужно вернуть
основной корпус: `python3 eval/index_corpus.py`. Иначе `run_eval.py`
посчитает метрики не на тех данных.

### Честно про качество генерации

Проверено вручную на ~10 вопросах. Работает неровно:

- **Надёжно**: отказ отвечать, когда ответа в чате нет («Какая зарплата у
  backend-разработчиков?» → «В найденных сообщениях ответа нет») —
  сработало во всех проверках. Короткие фактические вопросы («какую
  утилиту советовали», «кто такая Ника») — ответы точные и со ссылками.
- **Неустойчиво**: на вопросах, где ответ размазан по нескольким
  сообщениям, модель иногда подмешивает факты из соседних обсуждений или
  добавляет детали, которых в источниках не было.

Причина в размере корпуса: в чате 24 сообщения, поэтому топ-8 — это его
треть, и туда неизбежно попадает постороннее. Модель на 3B параметра на
такой шум реагирует плохо. На реальном корпусе в тысячи сообщений топ-8
был бы гораздо чище.

Качество генерации **не измеряется автоматически** — для этого нужна
отдельная разметка на достоверность (faithfulness), и это осознанно
оставлено за рамками: слой демонстрационный и на конкурсные метрики не
влияет.

### Галлюцинации на реальных данных

Проверка на импортированном Telegram-чате (живая переписка, много
безличных «он», «его» без имён) выявила два класса ошибок генерации.

**1. Подтверждение ложной предпосылки вопроса — исправлено.**
На вопрос «За что отчислили Якова Ивановича?» модель отвечала, что
такой человек отчислен, и додумывала причину. Имени «Яков Иванович» в
корпусе нет ни разу: модель подхватывала его из вопроса и встраивала в
ответ, а ссылки на источники создавали видимость достоверности.

Помогло правило: не переносить имя из вопроса в ответ, если его нет в
самих сообщениях. Проверено на контрольном наборе — регрессий нет,
результат даже улучшился (7/7 против 6/7).

**2. Путаница автора сообщения с субъектом события — не исправлено.**
На вопрос «кого отчислили» модель отвечала «Ян отчислили», хотя `Ян` —
это *автор* сообщения «Все кибербезники выпустились», а про отчисление
говорилось в других сообщениях безлично («его отчислили»). Имя берётся
из поля отправителя и приписывается чужому событию.

Попытка исправить промптом (правило «Автор — это тот, кто написал» плюс
явная разметка полей в контексте) **провалилась и была откачена**:
исходную ошибку не устранила, а работавшее правило про предпосылку
сломала — модель снова начала выдумывать причину отчисления.

Это уже четвёртая по счёту правка промпта, потребовавшая отката.
Закономерность: модель на 3B параметра надёжно держит порядка пяти-шести
правил, каждое следующее размывает предыдущие. Лечится не промптом, а
моделью побольше или отдельной проверкой ответа на соответствие
источникам (LLM-as-judge поверх сгенерированного текста).

**Практический вывод для продукта:** ответы такой системы нельзя
показывать как факты без возможности проверить источник. Поэтому под
ответом всегда печатается список сообщений, из которых он собран — это
не украшение интерфейса, а необходимое условие безопасного применения.

### Чего RAG не умеет по своей природе

Вопросы на **перечисление и подсчёт** («кто из участников писал X»,
«сколько раз обсуждали Y», «все случаи Z») этой архитектурой корректно
не решаются, и это не дефект реализации.

Наглядно: слово «привет» встречается в 14 сообщениях от 7 авторов, а в
контекст модели помещается 8 сообщений. Полный ответ физически не
собирается из того, что видит модель. Ситуация не лечится увеличением
контекста: на реальном корпусе в тысячи сообщений таких вхождений были
бы сотни.

Причина глубже размера окна: retrieval возвращает top-K **по
релевантности**, а не исчерпывающий список совпадений. Для «перечисли
все» нужен запрос к базе (SQL, полнотекстовый индекс), а не векторный
поиск. RAG отвечает на «что говорили про X», а не «сколько раз
встречается X».

Попытка обойти это промптом (правило «предупреждай о неполноте на
вопросах-перечислениях») была протестирована и **откачена**: модель на
3B параметра не отличает вопрос-перечисление от обычного — предупреждение
не появлялось там, где нужно, зато прилипало к обычным вопросам, а
качество остальных ответов падало. Ограничение честнее задокументировать,
чем обходить.

Оба скрипта используют только стандартную библиотеку Python — ставить
ничего дополнительно не нужно.

## Полученный результат

Прогон на 40 вручную размеченных вопросах (`eval/questions.json`) по
корпусу из 25 сообщений (5 чанков):

```
recall_avg = 1.0000
ndcg_avg   = 0.8739
score      = 0.9748   (recall_avg*0.8 + ndcg_avg*0.2)
```

Разметка покрывает 21 из 24 достижимых сообщений; вопросы намеренно
разного типа — с точными терминами (`goose`, `Inner Spark`, `CGO`),
с перефразировкой без общих слов («Программа падает сразу при запуске
на макбуке»), и с ответом из нескольких сообщений сразу.

Про то, почему `recall_avg` здесь ровно 1.0 и что из этих чисел
действительно осмысленно — ниже.

## Что дала возможность измерять: доработка ранжирования

Появившийся замер сразу показал дефект, невидимый без него. На вопрос
«Когда и в каком формате проходил митап?» нужное сообщение выдавалось
третьим — после двух реплик из чужого обсуждения («не оно?», «Не
похоже»), просто потому что они оказались соседями по окну чанкинга.

Причина: **ранжирование шло на уровне чанков, а выдача — на уровне
сообщений**. Чанк находился правильно и вставал первым, но его
`message_ids` разворачивались в хронологическом порядке — релевантность
отдельного сообщения внутри чанка не учитывалась вообще. Механизм для
этого в решении был (`keyword_score` в tier2), но на маленьком корпусе
он не включается: `tier1` набирает все 24 сообщения, не доходя до
своего лимита в 35.

Исправления в `search/main.py`:

1. **Реранкинг на уровне сообщений вместо чанков** (`rerank_messages`).
   Ключевая правка. Cross-encoder'у теперь отдаются отдельные сообщения,
   разобранные из `page_content` по тегам `[id|sender]`, а не чанки
   целиком — модель оценивает релевантность именно того сообщения,
   которое пойдёт в ответ. Побочный выигрыш: у reranker-API лимит
   считается в символах, а сообщения короче чанков, поэтому на ту же
   глубину уходит примерно на порядок меньше символов.
2. **Сравнение слов по основе.** `keyword_score` искал подстроку в любом
   месте слова и давал ложные совпадения: `"опрос"` находился внутри
   `"вопросы"`, `"дали"` — внутри `"передали"`. Заменено на сравнение по
   общему началу слова в обе стороны, что заодно чинит словоизменение
   (`"сисколла"` ↔ `"сисколл"`, `"митап"` ↔ `"митапы"`).
3. **Стоп-слова.** Вопросительные слова (`кто`, `что`, `как`, `когда`…)
   исключены из терминов запроса: они есть в половине сообщений, сигнала
   не несут, но раздували знаменатель в `keyword_score`.

Результат на одном и том же наборе из 40 вопросов:

| | nDCG@50 | score |
|---|---|---|
| Решение в том виде, в каком сдавалось на хакатон | 0.5718 | 0.9144 |
| После доработки | **0.8739** | **0.9748** |

Прирост `nDCG@50` — **+53% относительно исходного**. `Recall@50` остался
1.0 (он на этом корпусе насыщен, см. ниже), то есть весь выигрыш
пришёлся на порядок выдачи — ровно на то, что и чинили.

Разбивка по вопросам: улучшилось 32, ухудшилось 3, без изменений 5.
Средняя разница `+0.3021` при стандартной ошибке `0.0441`, 95%-й
доверительный интервал `[+0.2156, +0.3886]` — ноль в него не попадает,
то есть эффект не сводится к случайности выборки.

### Аблация: DBSF против RRF

Алгоритм слияния prefetch-результатов вынесен в переменную окружения
`QDRANT_FUSION`, чтобы выбор можно было проверить замером. Прогон обеих
конфигураций — `bash eval/ablation.sh`:

| Конфигурация | nDCG@50 | score |
|---|---|---|
| DBSF (по нормализованным скорам) | 0.8739 | 0.9748 |
| RRF (по рангам) | 0.8615 | 0.9723 |

**Разница статистически незначима** и решением считаться не может:
результат отличается всего у 5 вопросов из 40, причём 3 в пользу DBSF и
2 в пользу RRF; 95%-й доверительный интервал `[-0.0140, +0.0388]`
включает ноль. DBSF оставлен как значение по умолчанию, но честный вывод
здесь — **на корпусе такого размера выбор фьюжна не различим**, и для
обоснованного выбора нужен датасет на порядки больше.

Этот отрицательный результат оставлен в отчёте намеренно: он задаёт
планку, с которой стоит смотреть и на положительные — прирост от
реранкинга на уровне сообщений (`+0.30`) в 24 раза больше стандартной
ошибки, тогда как разница фьюжнов (`+0.012`) меньше неё.

### Побочный результат: измерение поймало ложное улучшение

Промежуточный замер показал, почему без метрики такие правки делать
нельзя. Версия с исправлениями 2+3, но без первого, дала **0.7786**
против **0.7881** у версии только с первым — то есть «очевидно
правильная» чистка стоп-слов ухудшила результат. Разбор показал
причину: исходный код набирал очки на случайном ложном совпадении
(`"дали"` внутри `"передали"`), которое случайно попадало в нужное
сообщение. Настоящий выигрыш дало только сравнение по основе слова.

## Честная оговорка про цифры

`data/Go Nova.json` — маленький пример чата (25 сообщений, из них 5
чанков после чанкинга; одно сообщение системное и текста не содержит,
поэтому достижимых id всего 24). Все retrieval-лимиты в `search/main.py`
(`RETRIEVE_K=100`, `TIER1_LIMIT=35`, `MAX_MESSAGE_IDS=50`) на порядок
больше размера этого корпуса — на каждый вопрос сервис возвращает все
24 достижимых id разом, поэтому `Recall@50` равен ровно 1.0
**независимо от качества поиска**: отсеивать на таком масштабе просто
нечего.

Единственная метрика, которая тут реально показательна — `nDCG@50`
(0.8739): она чувствительна к порядку выдачи, то есть напрямую
отражает, работает ли гибридный retrieval и rerank осмысленно, а не
просто выбрасывает всё подряд. Соответственно и итоговый `score`
(0.9748) на этом корпусе завышен: 0.8 его веса приходится на
насыщенный recall, и сравнивать это число с результатами на закрытом
датасете конкурса нельзя.

Стоит учитывать ещё одно отличие от условий хакатона: локальные модели
слабее тех, что давали организаторы (384-мерная MiniLM против
1024-мерной Qwen3-Embedding, квантованный jina-reranker против
llama-nemotron-rerank-1b). То есть `nDCG` здесь — скорее нижняя
оценка качества ранжирования, чем воспроизведение исходного прогона.

### Найденное ограничение локального реранкера

При разборе конкретного проседания («Для чего вообще создан этот чат?»,
`nDCG` 1.000 → 0.500) выяснились две вещи про квантованный jina-reranker,
которые стоит знать при чтении цифр:

1. **Оценки зависят от состава батча.** Один и тот же текст получает
   разный score в зависимости от того, что рядом: в замере сдвиг доходил
   до `-0.27`, чего достаточно, чтобы поменять порядок. Похоже на
   артефакт паддинга в квантованной ONNX-модели. На метриках это не
   сказывается — батчи формируются детерминированно, `run_eval.py` даёт
   ровно `0.8739` от прогона к прогону, — но абсолютные значения score
   сравнивать между разными наборами кандидатов нельзя.

2. **Модель слаба на чисто семантических вопросах.** На вопрос «для чего
   создан этот чат» она ставит «Железка MacBook Air (M1, 2020)» выше
   приветственного сообщения, объясняющего назначение чата, — и делает
   это даже когда тексты оцениваются поодиночке, то есть дело не в
   батчинге.

Именно на таких вопросах реранкинг на уровне сообщений проигрывает
исходной чанковой схеме: раньше нужное сообщение попадало наверх
«бесплатно», потому что оказывалось первым в своём чанке, а теперь
порядок целиком определяется суждением реранкера. Архитектурно это
правильнее (порядок обоснован, а не случаен), но качество упирается в
модель. С сильным реранкером организаторов картина, вероятно, другая —
проверить это без доступа к их API нельзя.

Поэтому результат `eval/run_eval.py` — это не попытка воспроизвести
позицию в лидерборде конкурса (для этого нужен закрытый тестовый
датасет, которого нет), а **подтверждение того, что весь pipeline
работает end-to-end офлайн**, плюс осмысленный (хоть и на маленькой
выборке) сигнал по качеству ранжирования.
